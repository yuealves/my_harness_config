# AI 协作与文档规约

所有 AI agent 在本仓库工作前必读：`AGENTS.md` → `docs/README.md` → `docs/design/0.overview.md` → 本目录全部 → 你要改的模块设计文档。

本文是交互方式与文档规则的唯一来源；`AGENTS.md` 只放摘要和入口。新会话即使不加载任何外部 skill，也按本文执行。

## 1. 每次需求怎么开始

- 除一句话能说清的小改动，先用 2–3 句复述：要解决什么、预期结果、本次范围。用户确认或纠正后再改文件。
- 同一轮给六点草案，每点一句，替用户写，不让填表：业务目的、支持场景、排除场景、不变量、失败约定、验收依据。已有答案复用，未定项标明。
- 只问影响业务、正确性或维护成本的问题，每轮 ≤3 个；每个给 2–3 个选项、业务后果和推荐；有选择题工具就用按钮。
- 对齐后直接执行，不重复求确认；已确认需求的续做不再确认。不擅自加功能、兼容或恢复机制；不支持的输入也要有明确行为。
- 改约定、扩范围或降验收时，只说“原约定 → 新发现 → 推荐调整”。
- 识别自然指令：“按推荐来”只接受当前列出的推荐；“展开第 N 点”只解释该点；“先做最小版本”给裁剪方案；“现在约定是什么”展示六点和未决事项。

## 2. 改造项目前先出方案

初始化新项目、把项目接入本规约、调整文档体系时：先只读审计，再给一屏方案（现状、目标结构、文件动作、不动的部分、验证方式、待定项），等用户明确同意后再改文件；“按推荐来”算同意。日常需求按第 1 节。

## 3. 文档体系

- 必需目录：`docs/design/`（是什么、为什么）、`docs/how-to/`（怎么做）、`docs/governance/`（什么不能变）；`docs/README.md` 是地图。
- 按需目录：`docs/validation/`（验证记录）、`docs/design/note/`（未定稿调研）、`docs/design/changes/`（需求文档）；不建空目录。
- 四类结构：变更/需求固定六点；Design 问题驱动、不套模板；How-to 固定步骤；Governance 每条规则写规则/为什么/检查。
- 长度预算：Design 正文 ≤2500 字，How-to ≤1500 字，变更 ≤1200 字；超出拆成摘要页 + 同名目录子文档，父文档单独可读。
- 同层 3–7 篇、粒度相近；层级 ≤3；每篇都能从 `docs/README.md` 沿父文档找到，不留孤立文档。
- 约定确认即落盘：中大型需求建 `design/changes/YYYY-MM-DD-<主题>.md`；小改动写进 Design 的“最近变化”；未定项标明。
- 实现或验证后补证据；完成后并入 Design，变更文档标“已合并”并冻结。
- 区分已确认 / 已实现 / 已验证 / 未验证 / 未定；结论附证据（文件:行、命令、测试）或标“未验证”。
- 当前事实只维护一处；历史文档不随代码更新；原始对话、草稿、日志不纳入 Git。

## 4. 工作方式

1. 设计文档先行：新增或大改模块前，先更新对应设计并与用户确认，再写代码。
2. 不做顺手重构：只改任务范围；发现的无关问题记录并报告。
3. 每个 commit 自包含验证：可编译 + 相关测试通过。
4. 遵守 `coding-standards.md`、`commit-conventions.md`、`invariants.md`。
5. 不确定就问：口径、语义、架构取舍先问，不猜。

## 5. 禁止事项

- 违反 `invariants.md`（除非用户明确拍板）。
- 未确认引入第三方依赖。
- 修改 `tests/fixtures/` 数据文件。
- amend 已 push 的 commit、force-push、提交密钥与内部地址。
- 把大输出命令直接灌进会话；先重定向到文件再取摘要。

## 6. 文档义务

- 新增模块：补 `docs/design/<编号>.<模块>.md`。
- 改模块交互：同步 `docs/design/0.overview.md`。
- 改规范：同步 `docs/governance/`。
- 每次交付说明：行为变化、实际验证、剩余限制、改了哪篇文档、待决事项。

## 7. 交付格式

一屏内给：行为变化、实际验证、剩余限制、改了哪篇文档、待决事项；细节按需展开。未运行的检查只能写成计划。
