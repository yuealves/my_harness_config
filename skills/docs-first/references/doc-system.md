# 文档体系

## 0. 原则

- 注意力是树：任一层读完都能停；父文档能单独读；子文档只在“细节值得单独查”时出现。
- 结构可预测：同类文档同一种骨架；状态、更新时间、上级和子文档永远在最前；细节永远在后面。
- 一处维护当前事实：历史文档冻结，过程交给 Git。

## 1. 目录与地图

```text
docs/
  README.md                 地图：三个目录各管什么、按意图怎么找
  design/                   系统是什么、为什么这样设计
    0.overview.md           总览（可按项目习惯换编号）
    <模块>.md               一模块一篇；过长时变成摘要页
    <模块>/                 子文档，与摘要页同名
    changes/                需求/变更记录（进行中和历史）
      2026-11-09-<slug>.md
    archive/                历史方案（如已完成的迁移计划）
  how-to/                   怎么做：构建、运行、排查、配置
  governance/               什么不能变，以及怎么检查
```

- 按**对象**分：总览、模块、横切能力各成一篇。不按开发阶段分（“第一阶段做了什么”不是设计）。
- 先沿用项目已有编号和命名，不另起一套；编号只表示阅读顺序，插入新文不必重排。
- `docs/README.md` 必须回答三件事：三个目录各管什么、按意图怎么找、哪些变更在进行中。
- 目录内文档超过 7 篇时，加该目录的 `README.md`，上级索引只留一句加链接。
- 不留孤立文档：新增文档必须在同一次修改里从父文档或索引链上。

`docs/README.md` 骨架（栏目可增减）：

```markdown
# 文档地图

- `design/`：系统是什么、为什么。先读 [总览](design/0.overview.md)。
- `how-to/`：怎么构建、运行、排查。
- `governance/`：什么不能变，怎么检查。

## 按意图找

- 第一次接手：总览 → 最常用的两个模块 → governance
- 改某个模块：design/<模块> → 它的子文档 → 相关 governance 条目
- 排查问题：how-to → design（时序、失败处理）→ governance
- 新增能力：governance → 相关 design → 写变更文档

## 正在进行的变更

| 变更 | 状态 | 待你决定 | 文档 |
|---|---|---|---|
| ... | 实现中 | ... | ... |

## 设计文档

- [总览](design/0.overview.md)：项目解决什么、模块怎么分
- [订单簿](design/3.order-queue.md)：逐笔事件的限价簿与队列

## How-to

- [构建与测试](how-to/1.build-test-run.md)：本机构建、跑测试、运行示例

## Governance

- [开发规范](governance/0.governance.md)：项目边界、正确性不变量、验证要求
```

## 2. 写给谁看

文档主要写给用户：他隔一段时间回来，要能快速接上。其次写给你自己：下次执行时能直接照做。不要写背景铺陈，也不要指望读者记得当时的对话。

- 用户会忘掉对话细节，但保留对模块和取舍的记忆。省掉客套和铺垫，保留“为什么”和“怎么核对”。
- 用户原话里的目的、例子、命名优先沿用；他确认过的写成结论。
- 用户只回“好、继续”的地方，标“待确认”，不算他理解并同意了细节。
- 你自己引入的概念：一句白话解释，或者不用。

## 3. 通用契约（所有文档）

1. 标题就是它回答的问题或对象；一篇只回答一个问题。
2. 前 4–6 行固定：回答什么 / 状态 / 更新日期 / 上级与子文档链接。
3. 同层同粒度：同类问题、相近篇幅，3–7 篇为宜；超过 7 篇通常说明这层混了两个抽象层次，先分组。
4. 可停：任一层读完能独立得到完整结论；父文档不依赖子文档才能读懂。
5. 长度预算：Design 正文 ≤2500 字（约 5 分钟），How-to ≤1500 字，变更 ≤1200 字，Governance 每条规则 ≤3 行。超出就拆；老文档在下次改到它时再拆，不专门重写。
6. 结论有证据：文件:行、命令、测试名；没有就写“未验证”。
7. 区分当前事实 / 计划 / 未定；历史文档冻结，不随代码更新。
8. 一个当前事实只维护一处，其他位置链接，不复制。
9. 用项目里的词；术语首次出现解释；段落 ≤3 句，列表优先。

## 4. 四类文档

### 4.1 Design：系统是什么、为什么

不套模板，具体问题具体分析。但必须回答下面这些问题，缺哪项由主题决定；**“问题与范围”和“代码对应”不能缺**：

- 它解决什么问题？不解决什么？
- 核心概念是什么？状态归谁所有，谁只能读？
- 关键流程和时序是什么？失败走哪条路径？
- 为什么这样设计？接受了什么代价？什么条件下要重估？
- 代码在哪里？入口文件、关键接口、对应测试。
- 哪些细节在子文档？每篇一句话说明讲什么。
- 还有哪些风险、未定项？

写法：标题可以用用户问过的问题，也可以直接用模块名；章节顺序按理解顺序，不按模板顺序；不写操作步骤（放 how-to），不写约束清单（放 governance）。

超过预算时变成摘要页加子文档：

```markdown
# 订单簿：逐笔事件驱动的限价簿与历史队列

> 回答什么：数据结构、更新时序、状态归属。
> 状态：已实现 · 更新 2026-11-09
> 上级：[总体设计](0.overview.md) · 子文档：[队列模型](order-queue/queue-model.md)、[撮合顺序](order-queue/matching.md)

## 结论
- 交易所簿与客户端簿分开，后者是前者的延迟视图。
- 同价位按价格-时间维护，撤单与成交同刻先撤后成。

## 为什么
...（≤2 句/条，细节在子文档）

## 代码
- 入口：`src/order_book/book.cpp:1` · 测试：`tests/cpp/order_book/`
```

摘要页仍受 2500 字预算约束，建议控制在 1800 字内，只留结论、关键表和链接；细节全部下沉到 `<同名目录>/`，父文档原路径保持不变，避免引用失效。

### 4.2 变更 / 需求：本次改什么

这类文档用来快速看进展，所以骨架固定。只在跨会话、需要独立验收或涉及多模块时创建；小改动直接更新 Design，并在状态块写一句“最近变化”。

位置：`docs/design/changes/YYYY-MM-DD-<slug>.md`。

```markdown
# <主题>：<一句话>

> 状态：实现中 · 更新：YYYY-MM-DD
> 最近变化：<结论变化 1–3 条>
> 要你决定：<无 / 1–3 条，各带推荐>

## 业务目的
## 支持场景
## 排除场景
## 不变量
## 失败约定
## 验收依据
## 当前状态与证据
## 还没定
```

- 六点每点 1–3 句，写结论，不写讨论过程。
- “当前状态与证据”写已实现、已验证、未验证和限制。
- 完成后：把当前行为并入对应 Design，本文档标“已合并到 X”并冻结，不再随代码更新。放弃时标“放弃”并写原因和留下的状态。

### 4.3 How-to：怎么做

骨架：什么时候用 / 前提 / 步骤 / 怎么确认成功 / 失败怎么办 / 相关文档。

- 步骤可直接执行，命令可复制，只写必要的解释。
- 设计原理不写在这里，链接回 design。
- 一篇只覆盖一个任务；任务变多就按场景拆，拆法与 Design 相同：入口页 + 同名目录子文档。

### 4.4 Governance：什么不能变

每条规则写四行：规则 / 为什么（≤2 句）/ 怎么检查（命令、测试或代码位置）/ 违反时怎么办。

- 能被机械检查的落到测试或 CI；不能的标“人工审查”。
- 规则给稳定位置（文件 + 小节号），其他文档引用而不复制。
- Governance 只放长期约束，不放一次性的实现细节。

## 5. 拆分、合并、归档

| 情况 | 动作 |
|---|---|
| 一篇超过类型预算 | 摘要页 + 同名目录子文档，父文档 ≤1800 字 |
| 父文档和子文档讲同一细节 | 删父文档细节，改成一句结论加链接 |
| 同层超过 7 篇 | 按对象分组（总览/模块/横切），不按阶段 |
| 两篇讲同一件事 | 合并，保留被引用的路径 |
| 内容过时 | 替换，或标“已过时，见 X”；不留两份“当前” |
| 阶段性计划、迁移方案 | 标“历史方案”，移入 `design/archive/`；当前设计另写 |
| 需求完成 | 变更文档冻结标“已合并”，Design 更新当前行为 |

## 6. 更新时机

- 约定确认后：建或更新变更文档，标出未定项。
- 范围或决定变化后：改受影响段落，重写“最近变化”。
- 实现或验证后：补状态与证据。
- 完成后：并入 Design，冻结变更文档，更新 `docs/README.md`。
- 每次只告诉用户：改了哪篇、哪些结论变了、还差什么决定。

## 7. Git 边界

- 纳入：design、how-to、governance、`docs/README.md`、可复现命令与结论摘要。
- 不纳入：原始对话导出、草稿、日志、大产物、重复总结。要保留的放 `docs/_local/` 并加进 `.gitignore`。
- 项目另有规定时以项目为准，例如禁止提交行情、模型和实验产物。

## 8. 保存前自检

通用：

1. 前 4–6 行能否说清：回答什么、状态、更新日期、上级和子文档？
2. 是否只回答一个问题，同层篇幅是否相近？
3. 有没有把计划写成现状、把未定写成已定？
4. 结论有证据，或明确标了“未验证”？
5. 是否超过类型预算？超了就拆。

Design 追加：

6. 父文档能否单独读？每个子文档是否都有链接和一句话说明？
7. 代码入口和测试路径是否真实存在？

变更追加：

8. 六点是否齐全？未定项是否写明谁决定？
9. 完成后是否已并入 Design 并冻结？
