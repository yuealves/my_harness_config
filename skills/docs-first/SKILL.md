# 文档先行

## 零、先分清场景

- **初始化新项目**（描述需求、要建新项目）：读 `references/init-project.md`，按模板生成文档骨架。
- **改造既有项目**（要求把当前项目接入本规范）：读 `references/adopt-project.md`，先审计再迁移。
- **日常需求**（项目已按本规范运行）：走第一、二节。

**初始化和改造都属于“改项目规范”：必须先给一屏方案（现状、目标结构、文件动作、不动的部分、验证方式、待定项），等用户明确同意后再动手。“按推荐来”算同意；只读审计可以直接做。** 日常需求按第一节处理。

## 一、先对齐，再动手

- 除一句话能说清的小改动：先用 2–3 句复述“要解决什么、预期结果、本次范围”，可先只读查证，等用户确认或纠正后再改文件。
- 同一轮给出六点草案，每点一句，替用户写，不让填表：业务目的 / 支持场景 / 排除场景 / 不变量 / 失败约定 / 验收依据。已有答案复用，未定项标明。
- 只问影响业务、正确性或维护成本的问题，每轮 ≤3 个；每个给 2–3 个选项、业务后果和推荐。有选择题工具就用按钮。
- 对齐后直接执行，不重复求确认；已确认需求的续做不再确认。不擅自加功能、兼容或恢复机制；不支持的输入也要有明确行为。
- 改约定、扩范围或降验收时，只说“原约定 → 新发现 → 推荐调整”。
- 识别指令：“按推荐来”只接受当前列出的推荐，“展开第 N 点”，“先做最小版本”，“现在约定是什么”。

## 二、文档：三层目录，按类型写

- 必需：`docs/design/` 讲系统是什么、为什么；`docs/how-to/` 讲怎么做；`docs/governance/` 讲什么不能变。`docs/README.md` 是地图和阅读路径。
- 按需：`docs/validation/` 放验证记录，`docs/design/note/` 放未定稿调研，`docs/design/changes/` 放需求文档；不建空目录。
- governance 固定四件：`coding-standards.md`、`commit-conventions.md`、`invariants.md`、`ai-workflow.md`。
- `ai-workflow.md` 记录交互方式、文档体系和工作方式；`AGENTS.md` 放摘要并指向它，这样新会话不加载本 skill 也能遵守。
- 先读现有索引与命名并沿用（含编号）；没有索引就建 `docs/README.md` 和首篇。
- 写或改文档前，必读 `references/doc-system.md`（通用契约、四类结构、拆分规则、生命周期、Git 边界）。
- 结构由类型决定：变更/需求用固定六点；Design 问题驱动、不套模板；How-to 固定步骤；Governance 每条规则写规则/为什么/检查。
- 长度是硬信号：Design 正文 ≤2500 字（约 5 分钟）、How-to ≤1500 字；超出拆成摘要页加同名目录子文档，父文档单独可读。
- 同层 3–7 篇、粒度相近；层级 ≤3；每篇都要能从 `docs/README.md` 沿父文档找到，不留孤立文档。
- 约定确认即落盘：中大型需求建变更文档，小改动写进 Design 的“最近变化”；都标未定项。实现或验证后补证据；完成后并入 Design，变更文档冻结标“已合并”。用户明确说不用记时不写。
- 当前事实只维护一处，历史文档不随代码更新；结论附证据或标“未验证”。

## 三、代码与提交规范

- C++ / Python 代码规范和 commit 规范以项目 `docs/governance/` 为准；新项目从 `references/templates/` 生成，替换占位符并删掉不适用的部分。
- 日常改动遵守项目已有规范；发现规范缺失或冲突时先指出，不擅自全库修改。
- 不做全库格式化或重写：只让新增和改动代码符合规范，存量在改到时再统一。
- commit 用英文 Conventional Commits，一个 commit 只做一件事；不 amend 已 push、不 force-push。

## 四、交付

- 一屏内给：行为变化、实际验证、剩余限制、改了哪篇文档、待决事项；细节按需展开。
- 未运行的检查只能写成计划；结论由证据支撑，不由叙述支撑。
